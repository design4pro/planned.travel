# 0048. Account session authority is primary and account scoped

Status: accepted
Date: 2026-11-03
Issue: #1758
Amends: SPEC §5/§6; CODE_REVIEW layering contract

## Context

Account security spans a person's workspaces. A tenant repository cannot model it faithfully. Better Auth 1.7.1 resolves session and verification blobs from KV before D1; deleting rows or exhausting the session index cannot make stale blobs cease granting authority. The existing `room-eviction.ts` sweep already handles missing indexes and must remain in use.

## Decision

`src/server/repos/account-security.ts` is one closed account-auth repository, separate from FU-3 and the tenant base. Its allowed records are the native `user` identity projection (`id`, `banned`, `banExpires`), native `session` rows, native `verification` rows restricted to the exact two-factor challenge and trusted-browser identifier shapes, and new account revision, session proof, verification proof, revocation operation and cleanup records, plus one global monotonic revocation-fence scalar. It cannot query `organization`, `member`, or tenant-content tables. Durable room targets contain workspace routing ids only; a queue acknowledgement may settle only its recorded operation/account/workspace triple. Native credential/factor reads and writes continue through Better Auth's adapter. No password, factor secret, backup set or provider token enters this repository.

A branded `AccountAuthScope` is issued only in `auth/account-authority.ts`. The subject comes from a native authenticated session or an internal native identity lookup during authentication, never an operation's client selector. The pre-authentication capability can read a revision but cannot authorize a revocation. Account mutations additionally require a verified current session and proof revision. A constructor accepting arbitrary request `userId` is forbidden. Allowed production callers are `auth/account-authority.ts` (proof binding and authority reads) and `auth/factor-management.ts` (register, commit and reconcile self-service operations). `auth/account-security-cleanup.ts` has a separate bounded system capability for keyset discovery of pending operation ids and account-bound encrypted cleanup references; it cannot accept arbitrary table/query names or return tenant content.

Each session and challenge/trust record carries immutable proof metadata. A request-local boundary wraps the native handler and each in-process API entry in `AsyncLocalStorage.run`; it never stores request state on shared auth context or shared adapters. Before invoking any endpoint, it reads the primary global revocation fence. Every revocation advances this singleton fence in the same winning-claim-gated batch as the account revision, and records that fence on the account. When identity is resolved, its last-revocation fence must not exceed the captured entry fence; otherwise the entire proof is refused. This ordering covers OAuth callbacks, direct social id-token login and email-verification auto-login, whose provider/JWT verification precedes local identity resolution in Better Auth. Thus even an unknown-subject proof has a snapshot before verification: entry fence, native proof verification, account revision whose last-change fence is no newer, conditional authority write. Never capture a fresh entry fence in a nested call. Capture known-subject account revisions before password/signature verification, then atomically compare them when recording new authority. Refresh never upgrades that revision. Pending two-factor proofs retain the original password proof revision across HTTP requests. Trusted-browser rotation preserves its trust revision. Direct HTTP and `auth.api` calls run through the same request-local boundary; wrapping only settings or SSR is insufficient. An old proof cannot be relabelled with the revision observed at session insertion.

After cutover, every session acceptance, refresh and trust bypass compares metadata against D1 primary authority. Missing/malformed metadata and read errors refuse authority. KV is a delivery cache only. Native expiration, bans, impersonation policy and OAuth/passkey TOTP exemptions remain in force. Trip-room connect/reconnect resolves the same session authority before forwarding identity; existing sockets close asynchronously through existing room eviction.

Registration is non-destructive and first issues an opaque restricted HttpOnly operation receipt. Commit requires a fresh non-impersonated self session, explicit confirmation and the matching intent. The receipt binds operation/account/session/expiry, permits only status reads and has a bounded post-commit grace. Status returns only operation outcome and cleanup state. Losing the registration response cannot authorize commit; losing the entire commit response can be reconciled without resubmitting a destructive operation.

The atomic commit uses a real D1 batch, never the sequential repository fallback. A winning conditional claim binds account revision, current session identity/token and freshness. Every later write requires this exact winning claim, including the revision increment, unchanged retained-session metadata update, other-session retirement, outcome and durable cleanup intent. A lost claim is a refusal with zero downstream mutations. Parameter count is bounded independently of session count. Other-device revocation does not alter factor or trusted-browser policy.

Old session rows remain a stable cleanup source until their encrypted token references have been durably recorded and attempted. Cleanup keyset-pages by immutable ids, refuses page/safety-limit errors, retries KV keys and workspace eviction independently, and reuses `collectSessionTokens`, `deleteSessionBlobs` and `trip-room-evict` where their interfaces preserve that stable source. Queue publication is an optimization; scheduled discovery retries durable pending work after restart/publication loss. No raw token is logged, projected in status or persisted in a new plaintext cleanup record.

## Rollout and rollback

Expand adds metadata and revision-aware writers/readers with enforcement and action disabled. Bounded backfill validates legacy sessions; cutover is refused until unversioned writers are retired and validation completes. Legacy browser trust is invalidated only at cutover. Cutover enables enforcement and the complete action together; missing metadata then refuses authority. Never roll back to a Worker that ignores authority after cutover; recover by a forward fix. No production deployment is authorized by this ADR.

## Required evidence

Before runtime implementation, independently review this concrete contract and the exhaustive inventory in `docs/account-session-authority.md`. Before completion, prove stale/re-cached blobs, refresh, concurrent sign-in, old challenges, failed CAS, actual batch rollback, cleanup restart, missing/stale/empty index, over-200/safety-limit paging, account/workspace isolation, lost entire response and two browser contexts at the named public seams. Measure primary D1 calls/latency and update the hot-path budget. The full validation gate and final independent diff review remain required.

## Implementation details established during review

Better Auth rebuilds `internalAdapter` after all plugin init hooks, so its one stable wrapper is installed after `$context` resolves. Per-request proof state remains in `AsyncLocalStorage.run`. Password sessions are inserted atomically with `password-pending` metadata and become accepted only after the complete native hook pipeline returns a successful matching token/user; unknown legacy trust cannot leave a provisional session accepted. Trust metadata records whether its lineage includes actual factor verification, so legacy trust rotation during expand cannot gain post-cutover authority.

D1 owns the irreversible cutover bit. The optional `ACCOUNT_SECURITY_ENFORCEMENT=active` deployment setting requests activation only after the primary bounded backfill validation succeeds; clearing that setting afterwards does not disable D1 authority. A missing singleton fails closed when activation is requested. Queue publication never acknowledges a room target: the existing `trip-room-evict` handler records acknowledgement after the actual fan-out succeeds, and pending targets survive publication loss and retries.

The existing erasure catalog `listWorkspacesHoldingUser` has one additional named caller: account-security room discovery. It projects only workspace routing ids from durable participation anchors, including a workspace the person has left, with 100 rows per keyset page and a 250-page refusal. Its erasure id is discarded. No scrub primitive is granted to this caller. D1 activation additionally requires the completed historical participant-backfill marker to have been validated and recorded; current memberships alone cannot prove historical coverage.
