## TLDR

Proposed: a completed password-sign-in factor change retires prior browser trust and other sessions, and disabling also requires current factor possession. This is a design-only successor to the enrolment specification; runtime behavior stays unchanged until independently reviewed implementation slices ship.

## Problem Statement

The enrolment surface exists, but factor management and session revocation do not yet form one account-security boundary. The policy must cover direct authentication endpoints, concurrent requests and partial storage failures as well as the settings screen.

## Scope and evidence

This specification coordinates one policy: changing password-sign-in factor authority retires the authority it replaces. Implementation is split into complete capabilities below. It does not implement universal MFA, recovery, SMS/email factors, plaintext code redisplay, new dependencies or production changes. The design PR uses `Refs #1156`, stays design-only, and is merged by a person. `afk-to-tickets` creates implementation tickets after merge; each needs security review of its own design and diff.

Verified at the authoring checkout with `better-auth@1.7.1` resolved in `pnpm-lock.yaml` and installed package sources, rather than inferred from current online documentation:

## Threat model and policy

Protect against a stolen password, a stolen older session, old trusted-browser cookies, impersonation, direct HTTP/in-process bypass, replay and concurrent factor/sign-in requests. A password plus an existing session is insufficient to disable an active factor. OAuth, Apple, Google and passkeys remain exempt from this TOTP challenge; an OAuth/passkey session does not authorize passwordless factor management. Compromise of the account email, provider account, authenticator or signing secret is outside this policy's protection.

All management reads/writes derive the account from a fresh, non-impersonated self-service session. Reject anonymous callers, challenge-only cookies and any `impersonatedBy` session before reading secrets. Reject supplied account ids rather than using them as selectors. An organization owner or platform administrator gets no self-service authority over another account. Account security is global to the person across their workspaces; tenant content and permissions remain tenant scoped.

| Operation              | Required proof                                                                  | Effect at commit                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Start enrolment        | Current password, fresh self session                                            | Create expiring proposal only; active factor and sessions unchanged                                                |
| Confirm enable         | Proposal-bound password authorization plus new-secret TOTP                      | Activate factor, retire all prior trust, revoke prior sessions, issue one new current session                      |
| Replace authenticator  | Current password and current TOTP or backup code, then new-secret TOTP          | Same lifecycle; old secret stays active until commit                                                               |
| Disable                | Password and current TOTP or one unused backup code in the same operation       | Disable factor, retire all prior trust, revoke prior sessions, issue new current session                           |
| Replace backup codes   | Current password and current TOTP or unused old backup code, fresh self session | Atomically replace set, retire prior trust, revoke prior sessions, issue new current session; display new set once |
| Sign out other devices | Fresh self session and explicit confirmation                                    | Keep current session, revoke all other sessions; preserve factor and trust policy                                  |
| Read remaining count   | Self session created less than 5 minutes ago, authoritative read                | Return only `{ remaining: integer }`; no secret/set/ids                                                            |

“Fresh” means session `createdAt` less than five minutes old, not a rolling `updatedAt`. Expired freshness requires a new sign-in, never silent refresh. Management commands additionally verify password in the request or in a single-use proposal authorization issued within five minutes. A cancelled/expired proposal never changes the active factor, sessions or trust. Failed proofs may change abuse counters, but no factor authority or session is revoked.

## Architecture and ownership

`src/server/auth/factor-management.ts` (new) owns orchestration, endpoint guards, proof validation and cookie issuance. A pure `factor-management-lib/` owns operation/state/error contracts and can be tested without Workers bindings. `src/server/auth/session.ts`, the auth adapter/plugin boundary and passkey plugin integrate authoritative acceptance; the same gate covers HTTP, server API calls, refresh, SSR/server functions and trip-room connect/reconnect. A UI-only wrapper around native calls is insufficient.

`src/server/repos/account-security.ts` (new) owns D1 batches and account-only projections. These global auth records cannot truthfully be scoped to one organization. The first implementation slice must therefore add a narrowly documented account-auth carve-out to SPEC §5/§6 and CODE_REVIEW, with an accompanying ADR, approved by security review before code lands. It uses a branded account scope minted only by the authenticated auth boundary, names its allowed production callers (`auth/factor-management.ts` and the authoritative auth adapter), and cannot query tenant content. Do not misuse an organization scope, broaden FU-3's read-only narrow projections into arbitrary mutation, or put SQL in auth/hooks/routes. Tenant writes continue through the existing tenant base, with tenant-isolation tests. This spec proposes that explicit bounded contract addition; it does not silently grant a current exception.

`src/server/auth/session-blobs.ts` remains the owner of exhaustive token enumeration and KV deletion. `room-eviction.ts` remains the owner of workspace discovery/eviction dispatch. Queue handling reuses `trip-room-evict` rather than adding a parallel close mechanism. Durable cleanup dispatch belongs beside existing account-erasure cleanup conventions; keep an account-security operation discriminator rather than mixing factor state into erasure state. `src/routes/_app/settings/-ui/` owns settings interactions. UI primitives remain data-free. Route loaders call validated server functions in `src/server/fns`; server functions call the auth service, never each other.

## Data model and authoritative acceptance

Add generated, additive migrations only. Proposed account-owned records:

- `account_security`: one row per user, `revision`, `trustRevision`, timestamps. Revisions are monotonically increasing integers; absent legacy row means revision zero only during the rollout below.
- Session security metadata: session id, user id, authentication revision, authentication method and proof completion time; unique session id, foreign keys and indexed owner. No credential values. Native session expiry, ban and impersonation checks remain mandatory.
- Trusted-browser authorization: identifier digest, user id, trust revision, expiry. Existing opaque cookie format may be retained, but native trust records without authoritative metadata cannot grant trust after cutover. Never return identifiers.
- Factor proposal: random id stored as digest, user id, initiating session id, base revision, operation, encrypted proposed secret/set, authorization time, expiry, committed operation id. One live proposal per initiating session/operation, five-minute expiry; cleanup removes abandoned encrypted material. No password or reusable possession proof stored.
- Completed operation: idempotency id/digest, user id, initiating session id, operation, committed revision and result category; no plaintext codes or raw session token in a status response.
- Cleanup work: durable token references encrypted at rest with the established auth encryption helper, workspace ids/continuation cursor, operation id, retry state. Retain source session tombstones until each intended key deletion has been durably recorded and attempted. Purge completed secret references under the existing retention conventions; cleanup is idempotent.

Every successful session/trust creation binds to the revision against which its authentication proof was verified. Re-read/CAS that revision before granting authority; never stamp a newer revision onto an older proof after waiting for a concurrent change. Pending 2FA challenges carry the base revision and fail if it changes. All sign-in methods, including exempt OAuth/passkey, participate in revision binding even though they do not ask for TOTP.

Every session acceptance and trusted-browser bypass checks the current D1 primary-authoritative security state. No KV revision cache or stale read replica may grant acceptance. A refresh must check before issuing/extending a cookie or writing an accepted blob. A missing/revoked row, revision mismatch, malformed metadata or storage read failure refuses authority. Re-cached old KV blobs remain invalid. This adds D1 cost to authenticated access; measure the added calls/latency before rollout and update ARCHITECTURE's hot-path budget. Do not promise a KV-only read path after cutover.

## Commit protocol, concurrency and failure outcomes

1. Resolve fresh self session and account; validate strict Zod schemas, origin/CSRF and rate limits. Read active factor, proposal, revision, password credential and session from authoritative storage. Reject locked password confirmation consistently with #1155. Hash/encryption and password verification happen before the batch, with version predicates rechecked inside it.
2. Validate possession without consuming it separately. Disable accepts a discriminated proof `{ kind: 'totp', code }` or `{ kind: 'backup', code }`. A TOTP is six ASCII digits for the current 30-second step with at most one adjacent step of clock skew; store the matched step, and refuse a step already accepted for a management mutation of that factor generation. Use the existing cryptographic primitive, not custom TOTP/crypto. Serialize consumption by account/factor revision. Backup replacement also requires current possession: otherwise password plus a stolen session could mint a new set and use it to disable the factor. A consumed old backup code is retired together with its old set in the replacement commit. Backup proof compares the stored encrypted set/version; consume with the mutation, not through a preceding `verifyBackupCode` request. Concurrent sign-in consumption and management consumption must share the same stored version/CAS.
3. Build one bounded atomic D1 batch. A conditional operation claim checks the expected account revision, live initiating session, credential version, proposal freshness and proof/set version. Every later statement is gated by the unique successful claim id. A zero-row CAS is not an exception and does not roll back a batch: all writes, including cleanup work, must require that winning claim. Test a deliberately lost claim and prove zero downstream changes. Require the atomic driver; never use `runBatch`'s sequential fallback.
4. The winning batch changes active factor/user flag and backup-set state, consumes proof/replay state, increments security and (for factor changes) trust revision, revokes old sessions, inserts one newly authenticated current session, records committed outcome, and durably records cleanup intent. Explicit other-device revocation advances session security revision and moves only the unchanged current session to it. Use account predicates/`INSERT … SELECT`, not one parameter per session. Statements stay within the repository's 100-bound-parameter ceiling; do not gather unlimited sessions into a batch payload.
5. Exhaustive D1-backed cleanup retains old session tokens/tombstones until keyset-paged, stable-source work is recorded. Reuse `collectSessionTokens`/`deleteSessionBlobs` where compatible with an immutable snapshot; concurrent inserts/deletes must not shift an offset walk. New authentication at the next revision is not accidentally cleaned. Retry all failed KV keys and workspace eviction independently; queue publication loss is recovered by a scheduled sweep of durable pending work. A queue is a delivery aid, not the only record that cleanup is owed.
6. Issue the replacement cookie only after D1 commit. KV population, publication or response loss after commit cannot roll back D1. Return/reconcile `committed`, `refused`, or `unknown`; never claim a post-commit error left the factor unchanged. Before every destructive commit, including one-request disable/replacement/revocation, a separate authenticated operation-registration request issues an HttpOnly receipt; the browser must receive that response before commit is permitted. Bind the receipt to operation id, account, initiating session, intended operation and a five-minute expiry, with a longer read-only reconciliation grace of fifteen minutes after commit. Status lookup accepts the fresh initiating session before commit or this limited receipt after it. The receipt authorizes only status, never a mutation, codes, tokens or general account access. A lost registration response means no commit; retry registration, not the destructive operation. Lost replacement cookies require sign-in under the final state. No raw token is returned by status lookup.

For ordinary pre-commit failure, all factor/session/trust state remains unchanged. Cleanup failures after commit leave revocation effective through D1 acceptance and work pending; show “changed, cleanup pending”, not a retry of the destructive operation. Same idempotency key plus different intent is a conflict; a repeated committed request reports status without consuming another code or issuing another credential. After a lost response, plaintext backup codes are not redisplayed by retry/status: explain that a new replacement is needed. Preserve the existing one-time display leave guard when the original response does arrive.

KV may retain stale blobs or verification cache entries for 60 seconds or longer, and the old refresh race can otherwise extend their life. This design closes future authentication acceptance through D1 rather than claiming globally instantaneous deletion. Existing in-flight requests may finish; trip-room eviction is asynchronous and closes all of the user's workspace sockets (including the retained device, which reconnects and rechecks authority). Never claim sockets close synchronously with a D1 commit.

## API Contracts and compatibility

New management API operations under `/api/auth/account-security/` are POST `register-operation` (idempotency key and operation kind; issues the precommit receipt), `prepare-factor`, `commit-factor`, `disable-factor`, `replace-backup-codes`, `revoke-other-sessions`, `operation-status`; count is GET `backup-code-count`. Use auth plugin endpoints with server-side checks shared with in-process callers, not routes that bypass the auth boundary. Input has no account id. `prepare-factor` accepts `operation: 'enable' | 'replace'` and password; returns proposal id, expiry and setup material in a no-store response. Replacement also requires current possession proof. `commit-factor` accepts proposal id, new-secret code and idempotency key; disable accepts password, proof and idempotency key; backup replacement accepts password, current possession proof and idempotency key. Status accepts operation id only. Revocation takes idempotency key. Strict validation rejects unsupported fields and invalid proof kinds.

Success returns operation id, committed status and final factor state; new backup codes appear only on the winning creation/replacement response. Count is an integer 0..10, authenticated and `Cache-Control: no-store`, never in shared/CDN/query persistence. Absent disabled factor means zero; unreadable/malformed encrypted material is a failure, never an invented zero. Count decryption is internal and cannot be logged or returned by an error. Never expose `viewBackupCodes` through a public wrapper accepting user ids.

Typed refusal codes cover fresh sign-in required, password session locked, invalid password, invalid/currently used factor proof, expired proposal, conflict, rate limit, unavailable storage, client upgrade required and outcome unknown. Reuse existing localized error mappings where exact; do not leak which other account or secret exists. Rate limits retain #1155's password budget, the existing account TOTP lockout (8 failures/900 seconds) and per-endpoint guard; failed destructive proofs cannot use fresh sessions to evade the account factor budget. Retry-After is respected, controls remain busy during a request, secrets never enter URLs, persistence, analytics or error capture.

Deployment is expand-and-contract across releases:

1. Add schema, authoritative validators, metadata-aware writers and default-off enforcement on every session/trust writer. Backfill live sessions at revision zero and test legacy refreshes. Do not activate revision-changing operations until the previous Worker version no longer writes unversioned authority. Public route paths and existing response fields remain accepted.
2. Enable authoritative acceptance everywhere. Sessions without metadata are accepted only through a bounded D1 validation/backfill path before activation; after cutover they require sign-in. Legacy trust cookies are deliberately invalidated, so the next password sign-in asks for the factor. OAuth/passkey exemptions persist. Account rollout status is D1-owned, never inferred from a client's bundle.
3. Ship new management UI with possession proof for backup-code replacement before retiring old management requests. At policy cutover close native `/two-factor/enable`, `/two-factor/disable`, `/two-factor/generate-backup-codes` and signed-in mutating `/two-factor/verify-totp` paths to unmediated calls, HTTP and in-process. Keep sessionless sign-in verification supported with revision checks; prevent alternate `method: otp`, `skipVerificationOnEnable`, key-display or backup-verify paths from mutating management state. Existing key display is a password-gated read. Old proofless disable cannot be translated securely: retain path/old shape parsing for one release and return localized `CLIENT_UPGRADE_REQUIRED` before mutation, inviting refresh. Do not add a required input to an existing server function. Document this intentional security refusal under BACKWARD_COMPATIBILITY's exception process in the implementation PR.
4. Activate factor-change guarantees only after all old writers are closed and security handler tests pass. Rollback after activation may use a forward fix or a revision-aware prior release; rolling back to a native unguarded Worker would revive old authority and is forbidden. Do not remove additive fields/tables in the same deployment.

## UI/UX

On `/settings/two-factor`, add remaining-code count, including a zero state with “Generate new backup codes”. Count loading has a stable skeleton; failure shows retry, never zero. Freshness expiry offers sign-in again and clears count. Enrolment/replacement uses the existing setup key, scannable-code and one-time backup-code panels. Leaving/cancelling setup discards only the proposal. A signed-in person with no password gets the existing set-password path; an existing OAuth/passkey session is not treated as password proof.

The disable dialog requires password and an explicit choice of authenticator or backup code. Switching proof type clears its value. Backup-code replacement reuses this proof selector and requires an old-set proof as well as password. Invalid proof remains an inline field error, not a generic success toast; busy state prevents double submit. Successful disable replaces the view with Off only after commit reconciliation. Stale factor/proposal conflict clears obsolete secret intent, reloads authoritative state and explains the next permitted action. Every destructive flow first registers its operation and receives the restricted receipt; a failed registration leaves the destructive action unsubmitted. Unknown outcome keeps an explicit check-status action; it must not invite a blind repeat or promise rollback.

On `/settings/security`, add independent “Sign out other devices”, confirmation, busy state and result. It keeps this device signed in and explains that other devices must sign in again; do not imply that browser trust or OAuth/passkey authentication is removed by this action. Factor-change confirmation separately states that all prior trusted browsers and other sessions will be retired.

Reuse existing dialog semantics, labelled fields, logical CSS properties and `CodeInput`. Provide a keyboard-operable proof selector, visible focus, field error association, always-mounted polite result region, focus on first invalid field and predictable focus return after cancel/success. Never render codes as unlabelled controls. Keep focus usable when refreshed state removes the triggering action. Secret/key/code panels and input subtrees remain `data-sentry-block`; do not capture auth responses in Sentry. Test light/dark at desktop/mobile widths and RTL Arabic.

## Phasing

Three independently usable capabilities share the account-authority policy. Phase 1 ships complete other-device sign-out; phase 2 ships complete safe factor management; phase 3 ships count-only visibility. Proposed infrastructure is delivered only with its first consumer. Do not ship dormant tables or a UI that promises controls its handler does not enforce.
