## TLDR

The Transport dialog holds one journey twice: ten endpoint fields on `TransportDraft` and a `ChainDraft` of N stations and N-1 Legs, with a `broken` flag that picks which copy is real and, as a side effect, what a save stores. This spec makes the chain the only place the journey's two ends live, renames the flag to the one thing it really decides (`savedAsLegs`: the save sends Leg rows, or the empty chain) and keeps both renderings the traveller knows. The issue's suggested direction, rendering the flat fieldsets as the two-station case of `ChainEditor`, is declined: it cannot be done without changes a traveller sees (listed below) for a benefit only the people maintaining the module get. Two tickets follow; the wire shape of a save, the server code and the copy do not change, and three small visible differences are listed below.

## Problem Statement

Engineers maintaining `leg-form.ts` and `leg-dialog.tsx` keep two representations of one journey in step by hand. Every place that touches a journey carries the decision of which copy is real: two builders (`flatChain`, `chainFromTransport`), two dialog wrappers (`chainFor`, `unbrokenChainFor`), an error allow-list for fields nobody can see (`CHAIN_OWNED_FIELDS`, `ChainOwnedField`, `blockingLegErrors`), a two-branch `recordEndpoints()`, and a seeding step (`breakIntoLegs`) whose only job is to copy the flat copy into the chain copy. The cost is drift: an endpoint typed in one copy and read from the other. One already shows today: the title suggestion (`suggestTransportTitle`) reads the hidden flat endpoints after the journey has been broken into Legs, so it can disagree with the stations on screen.

## The design

### One draft, held once

The chain is the only place a journey's two ends live.

- `TransportDraft` loses the ten endpoint fields (`departureName`, `departureCode`, `departureDate`, `departureTime`, `departureDayId` and the five `arrival…` twins). Everything else on it stays, including the record-level `carrier`, `serviceNumber`, `bookingCode` and `seat`.
- The first station holds the departure name and code, the first Leg the departure date, time and day; the last station the arrival name and code, the last Leg the arrival date, time and day. `leg-form.ts` owns two pure helpers over that mapping: one reads the ten fields out of a chain (`endsOf`), one writes a single field back (`withEnd`). Nothing outside `leg-form.ts` indexes into `stations` or `legs` to reach an end.
- A chain saved as no rows always has exactly two stations and one Leg. Only `splitLegAt` can change that, and it sets the persistence value in the same step. The module asserts the invariant in its tests; it adds no runtime guard for a state no function can produce.

### The persistence value: `savedAsLegs`

One boolean on `ChainDraft`, replacing `broken`. It decides what a save stores and nothing else.

| Question          | Rule                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it means     | The save sends the chain's rows, so the transport has Leg rows afterwards. Clear: the save sends the empty chain, so the transport has none.                                                                                                                                                            |
| Initial value     | `true` when the record has Leg rows; `false` for a record without any and for a new transport.                                                                                                                                                                                                          |
| What sets it      | `splitLegAt` (a stop added in the editor), `removeStationAt` (reachable only when it is already set), and the "Break this into legs" button.                                                                                                                                                            |
| What clears it    | Only the put-back control ("Put it back as one journey", `data-part="unsplit-leg"`). Nothing else in the dialog's form mode deletes Leg rows.                                                                                                                                                           |
| `chainPayload`    | Sends the empty chain exactly when the value is clear; otherwise the rows with platform, coordinates and timezone as held.                                                                                                                                                                              |
| `recordEndpoints` | One branch: the ten record fields always come from `endsOf(chain)`. Names and codes are trimmed as `chainPayload` trims them today (an empty one becomes null on the server); what is stored is what `saveTransportSchema.parse` returns, and the Phase 1 table asserts that, not the pre-parse object. |
| `recordZones`     | The two zones are sent only while the value is set, as today. A journey saved without rows never has its stored zones overwritten.                                                                                                                                                                      |

**Why it cannot be derived** from "the record had rows" and the station count. A record with one two-station row, opened as it is, and the same record after the traveller presses put-back are the same draft in every other respect (two stations, one Leg, the same rows underneath) and must save differently: the first keeps its row with platform, coordinates and timezone, the second deletes it. The record's history is constant across both, and so is the count. Something has to be in the draft, and it is this value.

**Naming.** `savedAsLegs`, the schema's own word for the rows (`transport_legs`) and CONTEXT.md's "Leg". Not `hasLegs`: every chain has Legs, a plain two-station journey has one. The glossary gets an entry with the first ticket (below) because the term is new.

### The two renderings stay

- Value clear: the two side-by-side fieldsets, reading and writing the chain's ends through `endsOf` and `withEnd`, with today's fields, labels, placeholders, arrival-day hint, live timing Alert, door-to-door line and the "Break this into legs" button.
- Value set: `ChainEditor`, then the put-back control.

The platform, timezone and catalogue search of the editor are not shown while the value is clear. They stay in the draft (a station keeps its zone and coordinates, a Leg its platform), so break, put back, break returns the same values.

### Validation

`validateTransportDraft` is split by what it validates, which deletes the field allow-list instead of maintaining it:

- fields of the record that are always on screen (title, distance, price, and the record-level pair): checked in both renderings;
- the journey's ends: today's flat rules, checked on `endsOf(chain)` while the value is clear; `validateChain` while it is set.

The dialog's `invalid` is "field errors, or the rules of the rendering on screen". Every error that blocks the Save button therefore sits on a control the traveller can see. `CHAIN_OWNED_FIELDS`, `ChainOwnedField` and `blockingLegErrors` are deleted.

### Deleted and kept

| Deleted                                                                                                                                                                                                                                      | Kept                                                                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `broken` (becomes `savedAsLegs`), `unbrokenChainFor`, `CHAIN_OWNED_FIELDS`, `ChainOwnedField`, `blockingLegErrors`, the unbroken branch of `recordEndpoints` and `recordZones`, the ten fields of `TransportDraft` and `emptyTransportDraft` | `flatChain`, as the reader of a record without rows (`chainFromTransport` calls it) and nothing else; `collapseToEnds` (new); `endsOf` and `withEnd` (new); `chainFromTransport`; `emptyChain`; `splitLegAt`, `removeStationAt`; `chainPayload`; `transportPayload(draft, chain, tripId)` with its signature |

`breakIntoLegs` shrinks to "set the value and copy the record-level service number and seat into the first Leg", because the ends it used to copy already are the chain's.

A new pure helper, `collapseToEnds(chain)`, is the put-back's reducer. It returns a chain with the first and last station, and one Leg: the first Leg's departure date, time and day, the last Leg's arrival date, time and day, and the first Leg's service number, platform and seat. The values of the other Legs and of the stations between are dropped, as today. It is called by the put-back control and by nothing else; the value is cleared in the same step.

## Decisions and Visible changes

The issue's suggested direction is not behaviour-preserving in five ways, and the chosen design keeps three visible differences of its own (below). Each was put to independent specialists with the code in front of them (rows 3 to 6 and 8 of the Resolved assumptions); each is decided here.

| #   | What the suggested direction does                                                                                                                                                                                                 | Decision                                                                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | "The N==2 case of `ChainEditor`" makes a station name mandatory; the flat form accepts blank places (a transport can be saved with only a title).                                                                                 | Names stay optional while the value is clear and are required once it is set, as today. No old record becomes unsaveable.                             |
| 2   | Error keys move: ordering errors land on `arrivalTime`, not `arrivalDate`; no time-needs-date rule; the live timing Alert and the door-to-door line are gone.                                                                     | The flat rules, the Alert and the door-to-door line run on the projection while the value is clear. The chain's rules apply only once Legs are saved. |
| 3   | "Break this into legs" as `splitLegAt(chain, 0)` opens three stations with a blank middle station that blocks the Save until it is found and deleted. Today's click opens the two ends on screen.                                 | Unchanged: the click sets the value and shows the editor on the same two ends. A third station is added only by the editor's own add-a-stop button.   |
| 4   | The editor shows platform, coordinates and timezone the flat form does not; typing a platform in an editor that saves no rows would be dropped, or would add rows without a stop having been added.                               | Hidden until the value is set. Nothing a traveller types is ever discarded, and no record gains rows by editing a field.                              |
| 5   | Put-back by repeated station removal keeps the outer stations as edited; today's put-back returns to the record's saved endpoints (for a record with rows) or to the flat fields as they were before the break (for one without). | Put-back keeps the outer stations as edited and drops the stations between them. This is the one deliberate difference, listed below.                 |

### Visible changes

1. **Put-back keeps edits to the first and last station.** Today, edits made to the outer stations inside the editor are discarded when the traveller puts the journey back; afterwards they are kept (name, code, the first Leg's departure, the last Leg's arrival). The stations between are dropped, as today. The label does not change and no copy is added: what put-back drops is a subset of what it drops now. Nothing is stored before the Save, and cancelling still discards everything.
2. **The title suggestion follows the stations on screen.** After a break, "Use ..." offered by the title field now reads the first and last station of the editor instead of the hidden flat fields. This removes a drift; it is a fix of the duplicated state.
3. **Break, put back, break keeps what was typed.** Today the second break rebuilds the chain from the flat fields and loses a platform, a zone or a per-Leg value entered in the editor between the two clicks; afterwards the chain is held once, so those values are still there. Nothing is stored in between.

Everything else is unchanged: layout, copy, fields, error placement and keys, the live timing feedback and the first click. What a save stores is unchanged for the same final on-screen state; the one flow where the stored result differs is changes 1 and 3 above: edit an outer station in the editor, put the journey back, save. The saved record then carries the edited ends (today it carries the pre-edit ones).

### Details the tickets must pin

- `endsOf` and `withEnd` take and return the field names of today's flat form, so the error keys of `validateTransportDraft` and the dialog's field wiring keep their type (`TransportErrors` is keyed by `keyof TransportDraft | 'form'` today, so once the ten fields leave the draft it is keyed by `keyof TransportDraft | EndField | 'form'`, where `EndField` is the union of the ten names; the keys themselves, `arrivalDate` among them, do not change); `withEnd(chain, field, value)` returns a new chain and `endsOf(chain)` returns the ten values as strings.
- The day of the first and last Leg after put-back comes from `collapseToEnds` (the first Leg's departure day, the last Leg's arrival day); no day is recomputed. Today a put-back shows the record's own day columns; the design shows the first and last Leg's day, and a save already overwrites the record's day with the first Leg's day (null when the Leg has none), so only the put-back path differs.
- A catalogue answer that arrives after put-back (the editor is gone) is ignored; focus is lost on put-back as it is on the first click (follow-up (e) below covers both).
- The dialog's local `chainFor` (`leg-dialog.tsx`, the initial-state builder: `emptyChain()` or `chainFromTransport`) stays, renamed to `initialChainFor` so that it no longer shares a name with the connection search's `chainFor`; no helper in `leg-form.ts` takes the name.

### Put-back control

It stays: same label (`modules.transports.chain.unsplit`), same `data-part="unsplit-leg"`, no locale key removed. It is shown whenever the editor is shown, which is a superset of "whenever the editor shows more than one Leg" and is what the code does now. The extra case matters: a record with exactly one Leg row has no other way to drop its row. Saving after put-back on a record that had rows sends the empty chain and deletes those rows; a record opened with one Leg and saved without pressing it keeps its row, with platform, coordinates and timezone intact. A two-station chain loaded with rows opens in the editor with platform and station details visible and editable.

## API Contracts and compatibility

None changes. `saveTransportSchema` and `transportChainInput` keep accepting both the empty chain and chains of two or more stations, byte for byte; no field is added or removed on the wire; `src/server/repos/transports.ts`, `src/server/fns/transports.ts`, `base.ts`, `schema.ts` and `drizzle/` are not touched. A tab loaded before the deploy and one loaded after it send the same wire shape (the values differ only in the flow named under Visible changes) (`BACKWARD_COMPATIBILITY.md` §2). If an implementation finds a server change necessary, it stops and risk is assessed again.

## Visual change expected

None, except the three results described under Visible changes (no layout, colour or spacing differs; no new state). Routes: the trip's transports screen, add and edit dialog. Light and dark, desktop and mobile, are the same as today, so the blind A/B visual check of the dialog (`docs/SPEC.md` §7) must find no difference. No e2e journey opens this dialog today, so the dialog's coverage is the unit and component tests of Phase 1 and 2, not e2e.

## Copy

No key is added, renamed or removed in any of the 23 locales. `modules.transports.chain.split`, `…splitHint` and `…unsplit` keep their text.

## Phasing

Two tickets, in this order. Both are complete on their own: after the first the codebase is honest about what the flag does, after the second the journey is held once.

## Implementation Plan

### Phase 1: name the persistence value, test the stored shape

Test first, independent of everything after it.

- Tests (write them first; the ones that exercise only existing behaviour pass at once and pin it, the others fail until the rename lands, then pass):
  - a two-station chain loaded from a record with rows, with non-null platform, latitude, longitude and timezones on both stations, saves those rows unchanged and not as the empty chain; its two zones reach the record payload; the whole payload parses through `saveTransportSchema`;
  - a chain with no rows that is split and then given a platform sends rows including the platform;
  - an old record opens and saves as no rows; put-back sends the empty chain; the existing `chainPayload` cases are kept or rewritten to the same effect;
  - `leg-dialog.test.tsx` characterises the dialog through its `saveTransportFn` mock: type the flat fields and save; break and save; break, put back and save; open a record with rows and save untouched. The expected wire objects are written down before Phase 2 and must not change in it;
  - a table of characterisation cases (record, edits made through the flat form) with the complete expected wire object for each, written against `transportPayload` and `chainPayload` so that Phase 2 re-expresses the inputs and must not change one expected output.
- Rename `broken` to `savedAsLegs` across `leg-form.ts`, `leg-dialog.tsx` and the tests; `breakIntoLegs`, `flatChain` and everything else keep their behaviour. Document the rule of the table above in the type's comment. Mirror the seven conditions of the 2026-10-03 ruling in the ticket's acceptance criteria, and run the docs grep named under Dependencies.
- Add the glossary entry to `CONTEXT.md` in the same change (a transport is saved as Legs when the save stores its Leg rows; a plain two-station journey is one Leg and is not saved as Legs unless the traveller breaks it up or it already had rows).
- Acceptance: nothing outside `src/components/modules/transports/`, its tests and `CONTEXT.md` changes; no locale key added or removed; the validation gate passes.

### Phase 2: the chain holds the ends

- Split `validateTransportDraft` as under Validation; delete `CHAIN_OWNED_FIELDS`, `ChainOwnedField`, `blockingLegErrors`, `unbrokenChainFor` and the unbroken branches of `recordEndpoints` and `recordZones`; shrink `breakIntoLegs` as described; make put-back call `collapseToEnds`; make `suggestTransportTitle` read the chain's ends.
