## TLDR

Proposed behavior: visitors browse published places on a categorized world map; members can also discover authorized workspace places and copy a place into a trip day. Publication is a separate reviewed snapshot, never a visibility flag on private content. This issue delivers design only; a person merges its design PR before `afk-to-tickets` creates implementation tickets.

## Verified baseline and scope

Category filtering, map clustering and trip-place creation already exist. Collections hold copies independently of trips. This design adds a public catalogue, reviewed proposals and discovery; paid placement, billing, photo editing (#1318), unrelated planner work and automatic imports are excluded.

## Data model and publication

Use the already-reserved global table names rather than a thirteenth platform table. `catalog_places` holds a publication snapshot with ID, revision, lifecycle (`ingested`, `review`, `published`, `retired`), explicit audience (`free-public` versus existing paid inventory), name, category code, point, public address/country, public summary and HTTPS website, public attribution/source and licence identifiers. Exact coordinates are approved explicitly for free-public navigation only. No private note, submitter identity, organization ID, trip ID or day ID is a public column projection.

`catalog_ingest` holds immutable submitted candidate revisions and private moderation metadata. `catalog_place_sources` / `catalog_sources` carry provenance and the approved source/licence record; never return raw payloads publicly. A tenant receipt stores organization, submitter, submission ID, state and revision, separately from global public fields. Existing collection/trip records gain no publication flag. Origin provenance on a copied trip place is a nullable catalogue ID and copied revision, with no cascading foreign key that can delete the snapshot.

Proposal flow: enter a public draft or select an already-authorized trip place. Collection-backed proposals are disabled until the canonical owner-private predicate ships; phase 1 never calls the current permissive collection readers. After that dependency, a readable collection source is also eligible. Every submission previews the exact public fields, requires explicit rights/provenance confirmation and then submits. There is no automatic copying of notes, internal descriptions, images, coordinates from a hidden source or personal attribution. Required fields are name (1-160), category, both finite coordinates in geographic bounds, provenance and a licence/permission basis; optional proposed summary at most 600 characters, address at most 500, website at most 2,048. Reuse tighter canonical validation where present. No HTML or automatic server fetch of user URLs. Images and attachments are excluded initially, avoiding publication of tenant R2 URLs or unlicensed media.

`docs/CATALOG.md` §§3, 5 and 7 own the shared field dictionary, provenance gate and lifecycle. Phase 1 must amend those sections together with SPEC and ACCESS before enabling this audience. This design adds an audience-specific extension, not a replacement paid-catalogue schema: retain the four paid `kind` values (`campsite`, `motorhome_stopover`, `wild_camping`, `service_point`) and all paid validation/publication rules. Add a separate nullable `discovery_category` with this design's six codes, required for free-public rows; it never substitutes for paid `kind`. Paid rows still require their existing `kind`; free-public-only rows may have null `kind`, with an audience-dependent database check. No automatic mapping promotes free-public rows into paid inventory, and changing audience requires both applicable guards and complete target validation.

Both audiences use the existing `ingested → review → published` lifecycle and `retired` withdrawal state; no stored `draft` status is added. Draft is an unsent UI form, pending/rejected are intake/receipt states, and rejection does not publish a catalogue row. A corrected published entry passes through review again; revival goes through review and direct ingested/retired-to-published transitions remain forbidden. Both audiences preserve the curator/admin-authored, non-blank publication `summary` of at most 600 characters; member text is candidate input, never trusted as curator-authored text. For free-public, the platform admin explicitly authors or adopts the reviewed summary in-product. Both audiences require the CATALOG §5.6 licence, attribution and linked source URL/name gate at publication, plus dictionary validation and unique slug. A manual proposal supplies a public provenance URL and source name, never a private source-record URL; missing provenance refuses publication. Existing paid curator rights stay intact; free-public transitions additionally require the admin-only `publicPlace` permission. Phase 1 tests both audience validators and every transition, proving paid behavior unchanged and alternate curator writers cannot bypass the additional gate. CATALOG's no-hard-delete policy remains unchanged; the unavailable-origin copy behavior below is defensive, not a new delete command.

A proposal starts pending. Reviewer may reject with a private reason, or correct the public candidate and publish a revision after reviewing its source/licence basis. Corrections to published entries are new reviewed revisions. Withdrawal sets retired; hard deletion, if later permitted by retention/erasure policy, also leaves copies intact. The public revision contains no pointer through which a visitor can resolve a private source. Audit records hold actor/action/entity/revision and necessary changes, never session secrets. Audit failure rolls back publication.

Submission ID is generated before the attempt and tenant-bound. Retrying the same ID returns the existing receipt/candidate; different payload with that ID is refused. Persist candidate and receipt together with a required D1 atomic batch assembled at the coordinating boundary from repository-owned statements. No sequential fallback; a driver without batch refuses before writes. Review commands require expected revision and state in the mutation predicate; two reviewers cannot publish/reject different versions by read-then-write. A concurrent loser reloads current state and shows a localized explanation.

## Permissions and contract amendments

Member intake is an explicit new exception to the catalogue mutation-permission contract, not a grant of `catalog:write`: the boundary requires a real authenticated TenantScope, verifies source access and provenance confirmation, and may only insert an immutable pending candidate plus receipt and audit. No publication/update privilege follows from its identifier. Document this exception in SPEC §5 and ACCESS with its one named handler, projection, limits and tests; reject calls missing verified submission authority before any SQL. The catalogue intake primitive receives verified authority plus a PlatformActor derived from the session, never client-authored actor data. Admin review and mutation continue to require `catalog:read/write/publish` as appropriate, plus the narrower permission below.

Implementation must add a narrow `publicPlace` platform permission resource with `read`, `write`, `publish`, granted only to platform admin. Keep existing curator `catalog` permissions unchanged for existing inventory; all generic catalogue writers must refuse free-public candidates and rows without the corresponding new permission. Otherwise a curator could bypass the new console via the old interface. Both guards apply when a command crosses catalogue audience; reject arbitrary audience changes from ordinary catalogue writes.

Update `docs/ACCESS.md` dictionary/grid/projections, `docs/SPEC.md` global catalogue rules, auth access types/tests, console consumers and every other permission-grid consumer/count in that same ownership slice. Published free-public read requires no session. Unpublished reads require the new permission. Existing paid-pack samples retain ten-row approximate-coordinate limits; being in a paid pack never makes a row free-public. Explicit publication is required for that audience.

No amendment is applied to live authority by this design-only PR. Later implementation must receive a fresh security and tenancy verdict on the completed design and diff before these changes ship.

## Discovery contracts, bounds and caches

Proposed public route `/explore` sits outside the authenticated layout. Detail uses a selected public ID in validated search state so links are bookmarkable without a private record ID. Existing signed-in navigation may link to it. Authenticated workspace results are a separate private request on the same screen; public responses never depend on cookies.

Public query: viewport `{west,south,east,north}` and zoom, category codes (at most eight), optional opaque keyset cursor. Validate finite values, latitudes -90..90, longitudes -180..180, south <= north; split an antimeridian-crossing viewport into two longitude ranges. No client-supplied SQL/order, offset, tenant ID or unbounded ID list. Sort by stable catalogue ID and return at most 200 rows plus a `hasMore` bit (read 201). Cursor is versioned, size-limited and bound to normalized viewport/categories; changed filters reset it. Unknown category or malformed cursor is validation failure. All queries contain published plus free-public predicates, including direct detail and origin resolution.

Each response has at most 200 points and all list entries correspond to exactly those points. Do not silently claim global totals or complete coverage. For `hasMore`, display a localized zoom/filter hint and next-page control; replacing a page replaces list and markers together. Client clustering is only for that page, never advertised as a global density count. Category counts, if shown, describe the loaded page. Signed-in mode splits the 200 displayed records into at most 100 public and 100 private records, with independent source cursors and a clear source label; switching source/page replaces its segment atomically. No unlimited accumulation of pages.

At zoom below 5, public discovery returns at most 200 fixed world-grid aggregate cells rather than individual public points, together with bounded accessible cell results. Use a fixed 20-by-10 longitude/latitude grid, canonical cell IDs and count capped/displayed as 200+; map and list show the same cells and category filter. Selecting a cell fits its bounds and fetches again; no private-source counts enter public aggregates. At zoom 5 or above, switch to the capped point/page contract above; the client-supplied zoom is validated as an integer 0..22 and is included in the cursor identity. Coarse cells can still be dense, so query-plan and latency checks apply to aggregation too. In combined mode, coarse public cells and the capped private segment remain explicitly different result kinds, each with list/map parity, never a misleading combined global count.

The row cap bounds response size and quadratic marker work, not database scan cost. Add query indexes for audience/status/category and geographic filtering, inspect query plans and measure dense/empty/world-wide reads with production-sized synthetic fixtures before enabling. A release fails its performance check if a worst-case request exceeds the implementation's documented Worker/D1 time budget; do not claim an index alone bounds scans. Do not bulk-fetch all rows to cluster. If this fails, a separately reviewed server spatial aggregation is required before rollout, not a new dependency slipped into the slice.

Initial responses use `Cache-Control: no-store` for both public and private discovery. No CDN, KV, service-worker, localStorage or persistence cache of place content. This deliberately avoids withdrawal invalidation races. Public and authenticated requests have distinct query-key roots; authenticated keys also include session generation, user ID, active workspace and normalized filters. Source revision and generation gate response application.

On sign-out, workspace change, membership loss or authentication refusal: abort old requests, increment generation, remove private query entries/selected details/dialog drafts, and replace the private layer before rendering public-only results. A delayed response cannot repopulate old rows. Server resolves the active workspace from session, never a client organization ID. No server HTML or hydration payload contains private discovery before authentication. Public SSR and caches cannot accidentally serialize the merged client view.

Withdrawn details become unavailable on the next read, without title/coordinates/reason. Clear an open selection when that read refuses. Browser memory already delivered to a reader cannot be recalled; document this limit to publishers. Refetch public results on focus and at most 60 seconds while the screen is visible. New reads after withdrawal must not return the entry; no-store plus the current DB predicate enforce that boundary.

Abuse controls are required on the server before DB work: reuse the existing hashed-IP key derivation with a discovery-specific fail-closed budget entry point, 60 discovery reads/minute/IP and a 200-row maximum; authenticated proposals 10/hour/user and 100/day/workspace with a 20-pending/user ceiling. Rate metadata uses existing retention policy and never returns identifiers. The existing `spendPublicBudget` catches backend errors and supports only minute buckets, so it cannot be used unchanged: add a separately named discovery policy with minute/hour/day windows and explicit unavailable/refused results, preserving existing credential-link behavior. Outage tests must prove reads and proposals refuse before database work. Rate-limit backend failure refuses the request; return localized retry state and Retry-After. Limits are product defaults, not claims of exact distributed atomic rate counting. Document/test the existing limiter's overshoot before rollout and use a serialized existing platform primitive if it cannot enforce an acceptable ceiling.

## Trip-day copy contract and recovery

`copyDiscoveryPlace` takes source kind/ID, destination trip ID/day ID and request ID. Zod validates all fields. A catalogue source is re-resolved through the current published free-public projection; a private source through TenantScope plus canonical audience checks. The client does not author the copy payload. The server checks destination trip write role, non-archived/editable state, day belonging to that trip, tenant category mapping and the existing places quota immediately at mutation time.

Create a trip-owned snapshot and assignment together through a required atomic D1 batch. Authorization, revision/state and quota conditions must be bound into writes, not only checked earlier. Each statement stays below `MAX_BOUND_PARAMETERS = 100` from `repos/batch.ts`; this operation is one copy, not bulk import. A failing/false guarded write must not commit its sibling: the implementation must prove rollback with the production batch interface and constraint-backed refusal, not assume that zero changed rows aborts a batch. Keep one request-result receipt with a uniqueness key scoped to tenant and destination; the same request returns the existing IDs without consuming quota twice. Reuse existing atomic-batch patterns; no interactive transaction and no sequential fallback.

The snapshot contains the accepted name, point, public descriptive fields and category mapping. It owns future edits independently. Preserve catalogue ID/revision as provenance, not a live title/point reference. Tenant source provenance must never enter a public response. Where a tenant category has no safe mapping, leave it uncategorized rather than creating a global category or trusting another workspace's ID.

Display trip data from the snapshot. A link to the catalogue origin is shown only after current public origin resolution succeeds. Retired/deleted origin shows a localized unavailable indicator with no hidden metadata; trip deletion, quota changes and catalogue withdrawal cannot cascade-delete a copy. A previously published ID alone grants no access. A source withdrawal committed before copy resolution refuses the copy; a concurrent withdrawal after a resolved authorized snapshot may leave that snapshot, equivalent to content already delivered. No claim of recalling copies is made.

On quota/role/day refusal keep the selection, reload permitted destination options, explain refusal and focus the picker heading. On lost response, reconcile by request ID before allowing another mutation; never invent a new ID to retry an unknown outcome. Keep committed place/day result even if follow-up itinerary reload or rollup enqueue fails. Publish existing trip-rollup events after durable copy; failure of that follow-up is reported/retried without copying again.

## UI/UX and Visual change expected

Desktop `/explore` has category controls, a results column, map and one selected-place panel. At 360px the same controls sit above a list/map switch; selected detail opens the existing sheet pattern. The map does not become the only way to discover or select a place. Reuse CategoryFilterBar, MapCanvas, PlaceMarkers, existing cards, dialog/sheet and focus conventions; no reference branding or parallel design system.

Pending responses retain old results only with an explicit loading indicator; mark them stale and disable their copy action until refreshed. Verify light/dark, desktop/mobile and keyboard/screen-reader flows during implementation.

Do not auto-publish or auto-copy after sign-in.

## Source policy, compatibility and rollout

Start with an empty catalogue. Accept manually entered member proposals and administrator-authored candidates under the same review, permission and audit rules. Each published revision needs a recorded permission/licence basis and any required public attribution; an unsupported assertion is rejected. No reference dataset, third-party geocoding results, private attachment or scraped source is imported. This is a software gate for review, not a legal commitment or approval of a particular licence. Any seed/import requires a separate verified source-policy decision and issue.

Generate only additive migrations via `pnpm db:generate`; no hand-written generated SQL, renamed columns or tighter old constraints. Add nullable origin fields and new tables/indexes without reinterpreting existing collection visibility. Old Workers must survive migration before deployment. Preserve existing route/server-function names and response fields; a new field on an existing input is optional for at least one release. New independent functions can require their initial fields. New sources never override stored user copy text.

Enable admin publication first, then anonymous discovery, then private discovery after its canonical privacy dependency, then trip copy. A server-owned rollout switch can disable entry points without hiding existing trip snapshots or deleting data. Rollback disables new mutations/read surfaces, retaining records/audit and allowing the old bundle to operate. Publication data cannot be recalled from already delivered clients or saved copies.

## Risks and alternatives

Publishing exact points is an intentional new audience contract, irreversible for content already downloaded. Explicit field preview, source rights, admin review and a distinct free-public flag are required. Live pointers into tenant records and reusing collection `public` were rejected because they widen access on a later private edit. A public cache was deferred because correctness on withdrawal is more valuable than speculative cache hit rates. Unlimited worldwide clustering and automatic third-party imports are excluded because their cost and licensing have no verified basis here.

## Design review

Independent staff architecture and scope-cohesion review approved this design after one correction: collection-backed proposals now wait for the canonical owner-private predicate, just like private discovery. Phase 1 supports manual and already-authorized trip sources only. Security/architecture decisions above are approved for specification work, not an implementation or source-licence approval. No runtime or visual behavior has been tested by the design review.
