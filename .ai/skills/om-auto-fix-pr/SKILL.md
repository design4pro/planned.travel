Extends the installed skill: read `.claude/skills/om-auto-fix-pr/SKILL.md` and follow it. Two additions.

**The `review-threads` label is a trigger, and the run consumes it in the same step that claims the PR.** When the PR carries it, the step-1 claim is the run's **first** tracker mutation and takes the label with it - before the worktree, the base merge or any push. After the three-signal read, `apply_label "in-progress" {prNumber}` first, then `remove_label "review-threads" {prNumber}`, then the assignee and the claim comment - the label leads `references/claim-pr.md`'s assign-first order here on purpose. Add before remove, so the PR is never observably free: `scripts/ci/review-threads-label.mjs` stands down on `in-progress`, and this run's own first push is a new head, the one thing that script's per-head marker lets through (#490) - the same swap `references/claim-pr.md` prescribes for `in-progress` -> `ci-monitoring` at release. When the three-signal read finds the PR held by another run - a live lock, not a stale one, and no `--force` (`references/claim-pr.md`) - stop without touching any label: the run knows the PR is held before its first mutation, and removing `review-threads` with no claim behind it would drop the ask for good, since the script never re-arms a head it already marked. Re-read the PR with **get-pr** right after the claim comment; when another run's claim comment surfaces there, the run whose claim comment is newer stands down: it posts a stand-down comment and stops, and removes neither `in-progress` nor the assignee - both are shared with the run that keeps the PR (one label, one bot account), and taking them off would reopen the #490 window under that run. A label still present is a run nobody took, the same contract `autofix` has on an issue. The `claude-review` job applies it when it leaves live threads (`scripts/ci/review-threads-label.mjs`), and the **Resolve blocking review threads** automation turns it into this run; leaving it on would let the next poll start a second run beside this one. Removing it is also what re-arms the trigger: the job re-applies it on the next head that still has open threads.

One addition to the stabilization loop's exit criteria:

- Before declaring the review approvable, run **list-review-threads** and require zero threads that are unresolved and not outdated. An open thread that the `om-auto-review-pr --autofix` stage fixed but did not resolve is closed here with **reply-review-comment** and **resolve-review-thread** (the repo override of `om-auto-review-pr` says how). An open thread the stage declined stays open and ends the loop with `changes-requested`, never `merge-queue`; the final report names the thread and its reason so a human can settle it.
