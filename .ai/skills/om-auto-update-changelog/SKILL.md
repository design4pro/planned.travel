name: om-auto-update-changelog
description: planned.travel extension of the installed om-auto-update-changelog skill. There is no version in the manifest - the topmost CHANGELOG.md heading is the version of record - and a release is a develop to main promotion.
---

Extends the installed skill: read `.claude/skills/om-auto-update-changelog/SKILL.md` and follow it. On top:

- **`--version` cannot be resolved from a manifest here, so resolve it from `CHANGELOG.md`.** `package.json` is `private` and carries no `version`, and there are no release tags; the reasons are in the header of `CHANGELOG.md` and they are deliberate. Read the topmost `# X.Y.Z (YYYY-MM-DD)` heading and propose the next number: **minor** when the window contains a `feat` a user would notice, **patch** when it carries only fixes and internal work. Never write a `version` into `package.json` to make the documented default work - that would create the second source of truth the header exists to refuse.
- **`--since last-release` does need handling once per entry, because the heading is a date and the window is not.** The installed skill searches `merged:>=${SINCE_DATE}`, an inclusive, date-only bound, and its only duplicate guard is "any PR number that already appears in an earlier entry" (`references/release-window.md`). An entry that _counts_ a pull request without _itemising_ it is therefore invisible to that guard, and anything merged earlier on the boundary date gets re-enumerated and attributed to the next version. So: **every entry records the exact commit it was enumerated up to**, and the next run drops any pull request whose merge commit is that cutoff or an ancestor of it, rather than trusting the date alone. `0.1.0`'s cutoff is recorded in its own note - `feefaecc7` (#676, 2026-09-21T05:52:57Z), the tip of `develop` the seed branch was cut from - so #674 and #676 belong to `0.1.0` and everything merged after it, #677, #675 and #695 included, belongs to `0.2.0`.
- **A release is a `develop → main` promotion** (ADR 0003). Leave `--release-ref` at its default `develop`: that is the branch the promotion is cut from and the one every pull request targets. Pointing it at `main` would build the window from what has already shipped.
- **`git describe` finds a tag here, and it is not a release tag.** The repository carries exactly one, `recovery/prd-167-base` (2026-09-01), left by an unrelated recovery. The installed skill reads `LAST_TAG` for two things and both misfire on it: reachability mode becomes the default whenever a tag and the release ref are both readable, which would window the release from a recovery point, and the boundary sanity check - "if `--since last-release` disagrees with `LAST_TAG`'s tagger date by more than 3 days, ask the user" - will fire on every release forever. Answer that prompt with the `CHANGELOG.md` heading, and force the documented degradation path (filter on `baseRefName == develop`, and say so in the report) rather than letting reachability run off that tag.
- **Run it on the open promotion pull request, before a human merges it** - `.github/workflows/promote-develop.yml` opens that pull request on the first push to `develop` and then leaves it open. **Its diff is not a frozen release window.** The workflow runs on every push to `develop`, so each later merge is carried into the same promotion pull request: anything landing between enumeration and the human's merge ships in that promotion without appearing in its entry, and is then attributed to the next version. So **capture the promotion head SHA when you enumerate, record it as the entry's cutoff, and re-check it immediately before the promotion merges** - if it moved, regenerate the entry over the new window or the release ships work it does not describe. The changelog lands as its own docs pull request against `develop`, which the next promotion then carries.
- **Reconcile the old housekeeping boundary before a new heading lands.** `om-close-fixed-issues` defaults to `--since last-release`, and that boundary only ever moves forward (`SDLC.md`, and the `CHANGELOG.md` header). Merging a new heading therefore makes every default sweep start at the new date, so any issue the old window never got to - a sweep that was capped by `--limit`, a sweep that did not run, or an issue skipped while it carried `blocked` or `in-progress` - stops being reconsidered permanently, not just until someone notices. Before the changelog pull request merges, run `om-close-fixed-issues` over the _outgoing_ window with a `--limit` wide enough to actually reach its start (the default 50 is a shorter reach than the date bound on an active week) and confirm it proposes nothing left. #697 is this pass for the pre-seed backlog only; every later heading owes its own.
- The changelog pull request is `documentation` and `skip-qa`: `CHANGELOG.md` is outside every path in `SDLC.md`'s QA routing.
