---
name: om-pr-autopilot
description: planned.travel extension of the installed om-pr-autopilot skill. The PR state is re-read before every push, because a human may merge or close the PR mid-run.
---

Extends the installed skill: read `.claude/skills/om-pr-autopilot/SKILL.md` and follow it. The following additions apply.

Diagnosis reads the PR state once, at the start, but a human may merge or close the PR while the run works. This rule covers every push the run makes, including those of the chained skills that push to the PR head (`om-auto-continue-pr`, `om-auto-continue-pr-loop`, `om-auto-fix-pr`, `om-auto-review-pr` in autofix), whether or not their own overrides were read:

- Immediately before each `git push` to the PR head, run **get-pr** and read `state`. Keep the check and the push in one command so nothing runs between them.
- Anything other than `OPEN` stops the run: do not push, release the claim, post one comment saying why the run stopped, and report the commits that were not pushed.

GitHub deletes a merged PR's head branch, and a push to it recreates that branch on the remote. It happened on money-tracker.online #447 (2026-09-24): the PR was merged while the base-merge gate ran, and the push that followed brought the deleted head branch back.

**"Approvable" in the state matrix follows the ruleset, not a habit.** A PR is approvable (row 9) when no review requests changes, no review thread is unresolved, and the base branch's ruleset requirements for approvals and code-owner review are met - with `required_approving_review_count: 0` and no code-owner review, that holds without any approving review. Read the ruleset exactly as `.ai/skills/om-approve-merge-pr/SKILL.md` step 3 says. A missing approval on a PR this run cannot approve itself (its own account authored it) is not a reason to stop at merge-ready under `--allow-merge` when the ruleset requires none.

**`--allow-merge` means a merge into `develop` only.** Every PR here, agent or human, is authored by the owner's one account, so the author tells nothing apart. A PR whose base is not `develop`, or that carries `do-not-merge`, ends at merge-ready under `--allow-merge` too: the `develop` -> `main` promotion deploys production and is the owner's to merge (`.ai/skills/om-approve-merge-pr/SKILL.md`).

- **QA runs through the unattended sign-off.** Where the chain reaches the QA stage (state matrix rows 7 and 10) of a PR that touches a user-facing surface, run `om-auto-qa-pr {pr} --self-qa-signoff` (the repo override of `om-auto-qa-pr` says how the sign-off is decided) instead of the evidence-only call. The installed "never applies the QA-approval label" rule binds the orchestrator itself, not the QA skill it dispatches; a `risk-high` PR still ends at merge-ready with the evidence posted, and `qa-approved` is the owner's. After a successful sign-off, re-read the QA labels and continue with row 9 under `--allow-merge` in the same run.

- **A spec-only PR ends at merge-ready, except the one `afk-plan-to-spec` opens.** A diff that touches only `paths.specs` is merged by a person, whatever `--allow-merge` says: the spec flow of `om-auto-write-spec` is "a human merges it" (AGENTS.md, `docs/agents/issue-tracker.md`). The exception is a spec PR written from a plan stage, which a specialist panel reviewed instead of a person: its branch is `spec/<slug>`, its body records the panel's verdicts, every spec it adds carries a `Plan` row (the generated `.ai/specs/README.md` aside), and it is not `blocked`. Under `--allow-merge` it goes through the state matrix like any other `develop` PR - row 3's specification review, then row 9, promoting a draft with **mark-pr-ready** first - and is squash-merged once CI is green (ADR 0033). Missing any of the four, it ends at merge-ready like the rest. Every other spec-only PR keeps the person's merge, the `om-auto-write-spec` flow's and a spec task's (`implement-ticket` writing the spec a request too large for a few slices needs; an `Issue` row and no `Plan` row) among them. A PR that marks delivered plan stages (`docs/plan-delivered-<plan-slug>`) touches only `docs/plans/`, so it is docs-only, not spec-only, and nothing in this rule stops it.

Four more rules cover the run and every chained skill, whether or not their own overrides were read:

- **A lesson stays in the worktree.** A lesson worth keeping goes in a `## Lessons` section of the PR body or the run's handoff file, where `afk-lessons` collects it. Never write it to `~/.claude/CLAUDE.md` or any other file outside the worktree: the write is refused under `dontAsk` and fails the run (runs b9d6b3a5, c9625ca3).
- **A fix Claude Code refuses to write is handed over, not forced.** When the fix needs a file the run may not write (`.husky/*`, `.claude/settings.json`, `.claude/hooks/*`), stop trying after the first refusal: never retry through `cp`, `sed`, `tee` or another path. Get a configuration guardian verdict through `.ai/skills/afk-decide/SKILL.md`, and end with the exact patch and that verdict in the PR body or the report, so applying it is one step for a human (run a9e39d80).
- **Find the dev server from the descriptor.** Read `baseUrl` from `.ai/qa/test-env.json` (`sh .ai/scripts/test-env-up.sh` writes it); never grep `.dev.vars*`, which the deny rules refuse. Quote every path that holds a variable, and never `cd` into a route path such as `src/routes/_app/trips/$tripId` unquoted: the shell expands `$tripId` to nothing.
- **Never try a denied command; use its allowed equivalent.** A command `permissions.deny` refuses ends the run on the first denial under `dontAsk` (run d232173a in money-tracker.online died on an improvised `git reset --hard origin/<branch>`). Move the worktree to the PR head with `git fetch origin <head>` and `git checkout -B <head> origin/<head>`, after checking `git status --short` is clean and `git log origin/<head>..HEAD` is empty: `checkout -B` refuses only when it would overwrite a local change, and it drops a local branch's unpushed commits. Never force-push a rebased branch (denied, `--force-with-lease` included): merge the base instead, or push a new branch. Never `--no-verify`: fix what the hook reports.
- **Never open a file `permissions.deny` lists under `Read(...)`, not even redacted through `cat` or `sed`.** It ends the run the same way (run b6eb30ef died on `cat .ai/qa/test-env.env`). The login's `passwordEnv` name is in `.ai/qa/test-env.json`; load the values with `set -a; . "$(jq -r .credentialsFile .ai/qa/test-env.json)"; set +a` and use `"$TEST_DEMO_PASSWORD"` in the command (AGENTS.md).
